# BLIBS.md

Short notes on the newer parts of the pipeline: loading technology data, converting it for the Vue app, and deriving deltas against older releases. See `CLAUDE.md` for the full picture (including the legacy vanilla-JS site under `old/`).

## Scripts

- **`index.js`** — entry point (`npm run conv`). Globs `definitions/**/*.toml`, parses all of them first (needed for `related`-id lookups), then calls `history.js` and `release-data.js`, then `convert.js` per file.
- **`convert.js`** — legacy output only: `old/config.json`, `old/html/<id>.html`, `old/deprecated.html`.
- **`history.js`** — derives each technology's ring-per-release history from git tags (`git show <tag>:<path>`); archives `old/releases/<version>/config.json` (legacy snapshot). Also exports shared helpers (`getReleaseTags`, `getFileAtTag`, `listDefinitionFilesAtTag`, `normalizeParsedConfig`) reused by `release-data.js`.
- **`release-data.js`** — writes `radar/data.json`: the current draft's entries + a `changes` block, in the shape the Vue app (`app/`) actually consumes.

## How release deltas are created

`release-data.js`'s `deriveAndArchiveReleaseData()` walks every release tag oldest→newest. For each tag it re-parses `definitions/**/*.toml` as it existed at that tag, and compares each technology's ring to its ring at the *previous* tag:

- no prior ring → `new`
- ring changed, now `DEPRECATED` → `deprecated`
- ring changed, otherwise → `moved`

That per-release `{entries, changes}` is written once to `radar/releases/<version>/data.json` and never rewritten (a published release is immutable). The Vue app's Changes page can also diff against any *other* past release on demand (client-side, same classification rules) via the "Compare with" picker.

## Where the generated files land

All paths below are build output (gitignored, regenerated by `npm run conv`), in the order `index.js` actually creates them:

| Step | File(s) | Created by |
| --- | --- | --- |
| 1. First pass | *(in memory only)* | `index.js` parses every `definitions/**/*.toml` |
| 2. Legacy release history | `old/releases/<version>/config.json`, `old/releases/manifest.json` | `history.js` → `deriveAndArchiveHistory()` |
| 3. New-app release history | `radar/releases/<version>/data.json`, `radar/releases/manifest.json` | `release-data.js` → `deriveAndArchiveReleaseData()` |
| 4. Current draft (new app) | `radar/data.json` | `release-data.js` → `writeReleaseData()` |
| 5. Per-technology loop | `old/config.json` (rewritten in full on *every* file), `old/html/<id>.html` | `convert.js` → `createCONFIG()` / `createHTML()`, called once per file from `index.js`'s loop |
| 6. Last | `old/deprecated.html` (`<tbody>` only, shell is hand-edited) | `convert.js` → `createDeprecatedPage()` |

So: anything under `old/` is the **legacy** vanilla-JS site's data; anything under `radar/` (`data.json` + `releases/**`) is the **new** Vue app's data. `radar/` also ends up holding that app's compiled build (`index.html`, `assets/`) once `cd app && npm run build` runs — the JSON files and the app bundle sit side by side there.

## Tests

`test/` holds unit tests for the pure conversion logic (built-in `node:test`, no extra test framework):

- `test/fixtures.js` — five reference technologies: one per quadrant (UI/Technology/Tools/Frameworks), one per ring (ADOPT/USE/HOLD/STOP), plus one `DEPRECATED` entry. Shaped exactly like what `js-toml`'s `load()` returns for a real `definitions/**/*.toml` file.
- `test/convert.test.js` — `json2config()` (quadrant/ring → the legacy int indices) for all four non-deprecated references; `createCONFIG()`'s validation (rejects a typo'd ring/quadrant, rejects a malformed `since`, accepts the deprecated reference without touching disk).
- `test/history.test.js` — `normalizeCase()`/`normalizeParsedConfig()` (the casing-typo tolerance), `validateForwardOnly()` (forward move/unchanged OK, backward throws), `getReleaseTags()` (real, read-only git call against this repo's actual tags).
- `test/release-data.test.js` — `buildEntry()` for all five references (full enriched shape, `recommendation` fallback, `since` only on the deprecated one, `related`-id resolution), plus `resolveRelated()`, `lastChangedRelease()`, `computeChanges()` (new/moved/deprecated classification and sort order).

File-writing wrappers (`createCONFIG`'s non-deprecated path, `createHTML`, `writeReleaseData`, `deriveAndArchiveHistory`, `deriveAndArchiveReleaseData`) are intentionally **not** exercised directly — they hardcode the real `old/`/`radar/` output paths, and calling them from a test would overwrite those (gitignored, but real) generated files with just the five test fixtures. Their logic is still covered indirectly through the pure functions they wrap (`json2config`, `buildEntry`, etc.); `fs.writeFileSync` is mocked (`t.mock.method`) where a test needs to assert "no write happened" (e.g. the deprecated-entry case in `createCONFIG`).

Run with:

```sh
npm test            # node --test
npm run test:coverage   # same, via c8 - prints a summary and writes coverage/ (html + lcov)
```

## TOML definitions layout: known delta

`template/info.toml` vs what real `definitions/**/*.toml` files actually use:

- **`since`** (format `YYYY-06`/`YYYY-12`, required only when `ring = "DEPRECATED"`) is used by real entries but **not documented in the template at all**.
- **`recommendation`** and **`related`** (`[config]`) exist in the template but **no real entry sets them yet** — template is ahead of content here.
- Ring/quadrant casing is normalized case-insensitively when reading historical TOML (`normalizeParsedConfig` in `history.js`) to tolerate old typos (e.g. `"Adopt"` vs `"ADOPT"`) — current files should still use the canonical casing (`ADOPT`/`USE`/`HOLD`/`STOP`/`DEPRECATED`, `UI`/`Technology`/`Tools`/`Frameworks`).
